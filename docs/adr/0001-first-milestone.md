# ADR-0001: Зберігання та межі першого функціонального етапу

Статус: прийнято для проміжного етапу.
Дата: 2026-10-03.

## Контекст

Початковий проєкт містив доменні сутності, XML-мапінги та SQL-резервування. Потрібно було отримати робочі Identity, Catalog, Pricing і базовий Inventory з API, зберігши існуючий Pricing Engine.

## Рішення

Прості операції з каталогом і довідниками використовують RecordStore з обмеженим переліком таблиць. Application формує записи лише після перевірки дозволених полів. Складські зміни та вибір цін винесені в спеціалізовані адаптери. User зберігається через ORM та реалізує Symfony Security interfaces в Infrastructure.

ModuleSchemaListener додає DBAL-таблиці до очікуваної схеми Doctrine. SchemaConstraintsListener додає зв’язки для UUID-полів. Це запобігає генерації DROP для таблиць і зовнішніх ключів, що не описані ORM-асоціаціями.

CHECK-обмеження підтримуються міграціями; їх виконання перевіряється прямими SQL-тестами. Міграції застосовуються до тестової БД до PHPUnit. Кожен інтеграційний або функціональний тест відкочує власні зміни.

Адміністративні HTTP-зміни та аудит зберігаються в одній транзакції. Повідомлення про помилки не містять SQL і трасування; сервер журналює непередбачені помилки з request_id.

Нові класи не містять коментарів і PHPDoc відповідно до вимоги власника. Для нетипізованого масиву атрибутів у зовнішньому VoterInterface залишено один точковий виняток PHPStan: missingType.iterableValue у StaffVoter, count 1. Рівень аналізу 8 збережено.

## Наслідки

Переваги: працюючі модулі без дублювання Pricing Engine, міграції узгоджені з Doctrine, контроль цілісності PostgreSQL та перевірені HTTP-сценарії.

Компроміси: універсальні записи stdClass слабші за окремі типізовані DTO; Identity Application ще залежить від власного security-адаптера. Це не повне виконання вимоги незалежності всього Domain від Symfony. Підключення Deptrac потребуватиме подальшого уточнення меж.
